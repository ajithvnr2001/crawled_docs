# インターネット全体のための認証局を構築する

![Steve Goldsmith](https://blog.cloudflare.com/_image?href=https%3A%2F%2Fblog.cloudflare.com%2F_emdash%2Fapi%2Fmedia%2Ffile%2F01KW497YX7768BEJGS24P0FMX8.png&w=64&h=64&f=webp&fit=cover&position=center)

12年前、Birthday Week 2014において、[ _Universal SSLを有効化し_](https://blog.cloudflare.com/introducing-universal-ssl/)、一夜にしてウェブ上の暗号化サイト数をほぼ倍増させました。Cloudflare背後のすべてのサイトに、一度も対価を支払ったことのないサイトも含め、無料でTLSを提供したのです。暗号化は高コストで時間のかかる取り組みではなくなり、デフォルトとなりました。

今年のBirthday Weekに際し、当社はその道における次の一歩を踏み出します。10年以上にわたって、当社はインターネット上で公的に信頼された証明書の最大の消費者の一つであり続けてきましたが、自らは一枚も発行したことがありませんでした。それが変わります。Cloudflareは、公的認証局（CA）となる意向を発表します。

本日、その取り組みにおける最初の具体的なマイルストーンを発表します。Chrome、Apple、Microsoft、Mozillaのルートプログラムへの組み込み申請を行い、GlobalSignから実績のある広く信頼されたルートを取得するための最終合意書に署名しました。これにより、発行開始日から最大限のデバイスカバレッジを持つ証明書を提供できるようになります。また、Chromeが最近発表した[ _Quantum-resistant Root Program_](https://blog.google/security/cultivating-a-robust-and-efficient-quantum-safe-https/)を対象に、ポスト量子証明書を提供する最初のCAの一つになる計画も発表します。

まだ証明書の発行は開始しておらず、開始まではもう少し時間がかかります。当社が行っているのは、この取り組みを公に表明し、マイルストーンが達成されるたびに共有し、ルートプログラムやWebPKIコミュニティの他のメンバーと協力しながら、構築しているものを正確にお伝えすることです。

## **信頼への二つの道**

まったく新しいルートは、何年間も広く活用できるようにはなりません。ルートプログラムに受け入れられた後も、そのルートは世界中のオペレーティングシステム、ブラウザ、デバイスに浸透しなければならず、更新を受け取れなくなったデバイスや、そもそも更新を受け取ったことのないデバイスの大規模なグループには到達できません。そうした古いクライアントの長いテールこそが、世界のインターネットトラフィックの大部分の発生源であり、相当数の回避可能な障害が潜む場所です。当社は、製造元、オペレーティングシステム、最終更新からの経過時間に関わらず、すべてのクライアントが可能な限り高いレベルのセキュリティを受けるべきだと考えます。

多様なクライアントにまたがるトラストストアの高いカバレッジを持つ既存のルートを取得することで、初日からその問題を解決します。既存のGlobalSignルートは2012年からブラウザ、オペレーティングシステム、デバイスで信頼されており、新しいルートでは決して到達できない古いクライアントにも届きます。ルートキープログラムへの組み込みに申請する新しいルートは、エコシステムが向かう方向、すなわち信頼されたルートの最大年齢を制限し始めているプログラムも含め、将来に向けて構築されています。確立されたルートは過去のデバイスへのリーチを、新しいルートは将来のポリシーの下での立場をもたらします。当社は、CAが発行する証明書がクライアントとの最も幅広い互換性を提供できるよう、その両方を求めています。

## **無料証明書の新たな源泉**

無料で自動化された証明書モデルは、現在では暗号化されたウェブの大部分を担っており、その多くが一つの注目すべきオペレーターを経由しています。Let's Encryptは1日に約1,000万件の証明書を発行し、5億以上のサイトにサービスを提供し、2025年には40億件のアクティブな証明書を突破しました。これは、インターネットに20年間で起きた最良の出来事の一つです。当社はその最大ユーザーの一つとして、そう断言します。

![](data:image/bmp;base64,Qk32BAAAAAAAADYAAAAoAAAACAAAAAgAAAABABgAAAAAAMAAAAATCwAAEwsAAAAAAAAAAAAA/////fz87+3t6+no8/Pz/P7/+fv77O7t////+/j46+Ti5t3b8Ozq+/v6+fr67Ovs////+fX06NvY4tLN7uTg+/j2+vn67ens////+vb06NrV4s/I7+Lc/Pj1/Pr68Ovt//////v57uLe6NjR8ujh//z3/v388+/x////////9u/s7+fi+PPs///7///+9/b2/////////fv49vXx/Pz3////////+/z5///////////9+fr2/v/7/////////P77)![](https://blog.cloudflare.com/_image?href=https%3A%2F%2Fblog.cloudflare.com%2F_emdash%2Fapi%2Fmedia%2Ffile%2F01M3NDPRKC82G6V4NTDZEF5NPP.png&w=715&h=477&f=webp&fit=cover&position=center)

その成功にはシステミックリスクが伴います。支配的な無料認証局が1週間不調に陥れば、ウェブの大部分には負荷を引き受けられる同等の無料・自動の代替手段が用意されていないことになります。証明書パックのレベルでは、当社は長年にわたって自社顧客向けにまさにこうした冗長性を構築してきました。Cloudflare Universal SSLの証明書には、すでにバックアップ証明書が付属しており、別の鍵でラップされ、別の認証局から発行され、プライマリが失効または侵害された場合に自動的に展開できる状態になっています。公的CAとは、同じ考え方をインターネット全体のスケールに拡張したものです。

導入を容易にするため、広く受け入れられているオープン標準プロトコルである[ _ACME_](https://www.globalsign.com/en/acme-automated-certificate-management)（Automated Certificate Management Environment）ファーストを採用します。ACMEによる自動化された発行と更新が、当社から証明書を取得する方法となります。これは、既存の無料CAを利用している人であれば、ディレクトリURLを変更するだけで当社に移行でき、新しいツールも、アーキテクチャの再設計も不要であることを意味します。

## **証明書の成長予測は非常に大きい**

Cloudflareはグローバルなインターネットリクエストトラフィックの20%以上の前面に立ち、数百万のドメインのTLSを終端しており、そのために年間数百万枚の証明書に依存しています。当社はそれらの証明書を複数のCAを通じてプロビジョニングし、CAの障害や失効イベントが発生してもカスタマーサービスが維持されるよう、プライマリとバックアップのパスを用意しています。

これにより、WebPKIエコシステムがどのように機能するかだけでなく、消費者側として、困難な形で時折失敗することも学びました。レート制限、検証のエッジケース、失効レイテンシ、チェーン構築、ルート配布の遅延に対処してきました。近年のCAの変動を経験し、またその影響を、顧客を通じて実感しています。外部から見た信頼性の高い発行とはどのようなものかを知っています。なぜなら、お客様の稼働時間は、発行者が不調な日でも当社の回復力と迅速な対応にかかっているからです。

そして、今後数年で[ _証明書の最大有効期間が短縮され_](https://cabforum.org/2025/04/11/ballot-sc081v3-introduce-schedule-of-reducing-validity-and-data-reuse-periods/#ballot-contents)、エージェント的な活動が増加し、PQ証明書が主流になるにつれ、当社が年間依存する証明書の絶対数は急速に増加し続けると予想しています。そしてこれは当社だけの問題ではありません。この問題を自分たちだけのために解決するだけでなく、インターネット全体にこのユーティリティを提供する一翼を担い、お客様の証明書サプライチェーンにさらに多くのプロバイダーを確保したいと考えています。

## **レジリエンスのための設計：透明性と「fail small」**

自らCAになるというこの新たな責任を担うにあたり、当社は可能な限り信頼性が高くレジリエントなCAを構築することを誓います。ミスを避けることだけでなく、Cloudflareの他の製品と同様に「fail small」を実践し、あらゆる問題の影響を限定する、そのような認証局を構築するつもりです。

それは、インシデントが発生する前にリカバリーの設計とテストを行うプロセスを制定することを意味します。例として、更新の自動化を発行の条件とします。RFC 9773で標準化された[ _ACME Renewal Information_](https://www.rfc-editor.org/info/rfc9773/)（ARI）をサポートするクライアントにのみ発行します。サブスクライバーは、更新エンドポイントをポーリングし、当社が公開する更新ウィンドウに従って行動し、更新対象の証明書を識別する自動化を維持しなければなりません。

過去16年間で観察してきたことからも学んでいます。あまりにも多くのサブスクライバーが証明書を迅速に置き換えられなかったため、タイムリーな失効とサブスクライバーのサイトのオンライン維持の間で板挟みになった認証局を目にしてきました。コンプライアンス上の問題やセキュリティインシデントなど、証明書を廃止する必要がある場合、影響を受ける証明書の更新ウィンドウを前倒しし、利用可能な時間にわたって置き換えを分散させ、代替証明書の発行を追跡することができます。

これは当社が構築しようとしている多くの方法のうちの一つに過ぎません。発行スタックと運用を透明化し、証明書に署名するソフトウェアの再現可能なビルドを公開し、鍵を保管するハードウェアセキュリティモジュールを証明し、発行の健全性とインシデントのための公開ダッシュボードを運用します。監査は特定の時点における評価であり、CAが合格したことを示すものであって、通常の火曜日にどのように運営されているかを示すものではありません。当社は、ルートプログラム、研究者、そして一般のサイトオーナーが、監査と監査の間に現代のCAが実際にどのように運営されているかを観察できるようにしたいと考えています。

## **ポスト量子インターネットのための認証局**

当社はまた、証明書が現在どこにあるかだけでなく、どこへ向かっているかについても主導する意向です。2027年第1四半期に最初の証明書を発行することを目標に、Merkle Tree Certificates（MTC）を本番環境で発行する最初のCAの一つになる計画です。

MTCは、従来の証明書チェーンがTLSハンドシェイクに負担をかけるほど大きくなるポスト量子の世界向けに設計された、公的に信頼された証明書をより新しくコンパクトに届ける方法です。当社はIETFでMTCの[ _標準ベースの提案_](https://datatracker.ietf.org/doc/draft-ietf-plants-merkle-tree-certs/)を推進してきました。そして今年初め、[ _ChromeはMTCをポスト量子認証の推奨パスと指定しました_](https://blog.google/security/cultivating-a-robust-and-efficient-quantum-safe-https/)。本番環境でMTCを発行することで、ウェブ全体が行わなければならない移行に実際のボリュームをもって取り組みながら、Cloudflareのお客様とより広いインターネットをポスト量子の脅威から守ることができます。MTCとこの新しいWebPKI（公開鍵基盤）がどのようなものになるかについては、[ _このトピックに関するブログ記事_](http://blog.cloudflare.com/pq-ca-with-mtcs)でさらに詳しく共有しています。

その移行が急激なものになるとは考えていません。インターネットの多くは、さらに何年もの間、クラシックな証明書と既存のWebPKIに依存し続けるでしょう。しかし、その期間にわたって、MTCが発行シェアを着実に拡大していくと期待しています。だからこそ、当社は両方に対応する一つのサービスを構築しているのです。クラシックな証明書とMerkle Tree Certificatesを一つのCAのもとに、一つのライフサイクルと一連の保証で提供することで、お客様は自分たちのペースで採用し、ハードカットオーバーなしにウェブが移行するのを助けることができます。数十年にわたる移行においてどちら側を選ぶか、二つのシステムを運用するか、バランスが変わったときに再構築するか、という選択をお客様に強いるべきではありません。

## **いつも通り、CloudflareはCustomer Zeroとなります**

お客様向けにUniversal SSLを通じて証明書パックを提供することに加え、Cloudflareはシステムと内部運用の運営のために多くの異なるCAから証明書を調達しています。他の製品と同様に、新しいCAとその証明書（WebPKIとMTCの両方）の[ _Customer Zero_](https://www.cloudflare.com/the-net/top-of-mind-security/customer-zero/)となり、新しいシステムとプロセスのすべての側面が当社の高い内部基準を満たし、CAのインフラがCloudflareスケールで稼働することを確認します。

## **今後の展開**

当社は、主要なウェブルートキープログラムのそれぞれとの申請・承認プロセスを進めています。これらのプロセスはオープンに進行し、2027年初頭の最初のMerkle Tree Certificatesに至るまで、随時アップデートを共有していきます。この取り組みをフォローしたい、または将来Cloudflare CA証明書を最初に使用したいという方は、[ _アップデートに登録_](http://cloudflare.com/resource/certificate-authority)できます。また、Cloudflare内でこの新たな機能の構築に参加したい方は、[ _採用しています_](https://boards.greenhouse.io/cloudflare/jobs/8237801?gh_jid=8237801)！

この新たな機能を構築していく中で、当社は長年（実に16年間）依存してきたパートナー公的CAのネットワークと引き続き緊密に連携し、信頼でき、オープンなインターネットを確保するために共に取り組んでいきます。

Universal SSLを立ち上げた時、議論はシンプルでした。インターネット上を暗号化されて流れるすべてのバイトは、傍受、スロットル、検閲をより困難にし、オープンなウェブは当社の全従業員が共に構築するものです。公的で冗長性があり透明な認証局とは、その同じ議論を一段下に持ち込むことです。暗号化されたウェブをそもそも可能にしている信頼そのものへと。当社は長い間この目標に向けて取り組んできており、ついに道を歩み始められることを喜ばしく思います。

Happy Birthday Week!
